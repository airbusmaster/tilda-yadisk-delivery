# Автовыдача цифровых товаров: Тильда → Яндекс.Диск → письмо покупателю

Маленький сервис на одном файле: принимает вебхук Тильды после оплаты,
подбирает файлы по артикулам, выдаёт покупателю персональные ссылки и
присылает владельцу отчёт в Telegram. Файлы хранятся в публичной папке
Яндекс.Диска — платить за хранение и перекладывать гигабайты никуда не нужно.

Написан под реальный магазин цифровых гидов: PDF по 20 МБ – 1 ГБ, несколько
заказов в неделю, владелец до этого рассылал ссылки руками.

Только стандартная библиотека Python 3. Ни зависимостей, ни докера, ни базы —
SQLite рядом с файлом.

## Зачем это, если можно просто дать ссылку на Диск

Публичная ссылка на папку одна на всех: её пересылают, выкладывают в чаты,
и вы об этом не узнаете. Здесь у каждого заказа своя ссылка с собственным
сроком жизни и лимитом скачиваний, а в админке видно, кто сколько раз скачал.

## Главная причина, по которой сервис качает файл сам

Первая версия просто редиректила покупателя на временную ссылку Яндекс.Диска.
Покупатели жаловались, что ссылка не работает, а в логах при этом был честный
`302` — со стороны сервиса всё выглядело исправным.

Причина: **`downloader.disk.yandex.ru` отвечает `403 Invalid Referer` на любой
запрос с заголовком `Referer`.**

```
без Referer                        → 200, файл отдаётся
Referer: https://e.mail.ru/        → 403 Invalid Referer
Referer: https://mail.google.com/  → 403 Invalid Referer
Referer: https://ваш-домен.ru/     → 403 Invalid Referer   ← даже свой домен
Referer: (пустой заголовок)        → 403 Invalid Referer
Referer: https://disk.yandex.ru/   → 200
```

Браузер сохраняет реферер исходной страницы при переходе по редиректу. Значит,
покупатель, открывший письмо в веб-почте (mail.ru, Gmail, Яндекс.Почта),
приносил на Яндекс реферер почтовика и получал 403. А тот, кто читал письмо
в нативном приложении, реферера не приносил и всё скачивал. Отсюда
«у одних работает, у других нет» и полное отсутствие следов в логах.

Лечится это двумя способами, и в сервисе сделаны оба:

1. Страница-посредник `/d/<токен>` с `<meta name="referrer" content="no-referrer">`,
   `rel="noreferrer noopener"` на кнопке и заголовком `Referrer-Policy: no-referrer`.
2. Отдача файла своим потоком через `/f/<токен>` — покупатель на Яндекс вообще
   не ходит, так что его реферер ни на что не влияет.

Заодно страница решает вторую проблему: мгновенный редирект на файл в 300 МБ
выглядит на телефоне как «нажал, и ничего не произошло». Теперь покупатель
видит название, размер, кнопку и подсказку, где искать скачанный файл.

## Как работает

```
оплата в Тильде
      │  webhook (только после оплаты)
      ▼
POST /hook/<WEBHOOK_SECRET>       товар → артикул → файл в catalog.json
      │
      ├─→ письмо покупателю со ссылками /d/<токен>
      └─→ отчёт владельцу в Telegram

GET /d/<токен>   страница с кнопкой (реферер срезан)
GET /f/<токен>   сервис качает файл с Диска и переливает покупателю
```

Скачивание засчитывается только когда файл доехал до конца. Оборванная
загрузка лимит не тратит, докачка по `Range` поддерживается — это важно,
когда файл на 300 МБ качают с мобильного интернета.

## Установка

```bash
git clone https://github.com/<вы>/tilda-yadisk-delivery.git /opt/delivery
cd /opt/delivery
cp config.env.example config.env      # заполнить
cp catalog.example.json catalog.json  # свои товары
python3 set_tg_chat.py                # подставит TG_CHAT_ID
cp deploy/delivery.service /etc/systemd/system/
systemctl enable --now delivery
```

Сервис слушает `127.0.0.1:8091` — наружу его выставляет nginx,
пример конфига в `deploy/nginx.conf.example`. В нём для `/f/` отключена
буферизация: иначе nginx будет спуливать гигабайтный файл на диск, прежде чем
отдать хоть байт покупателю.

Бэкап базы выданных ссылок — в крон:

```
0 4 * * * /usr/bin/python3 /opt/delivery/backup.py >> /opt/delivery/backup.log 2>&1
```

## Настройка

Всё в `config.env`, см. `config.env.example`. Обязательное:

| ключ | что это |
|---|---|
| `PUBLIC_BASE_URL` | домен, с которого раздаются ссылки |
| `YADISK_PUBLIC_KEY` | ссылка на публичную папку Яндекс.Диска с файлами |
| `WEBHOOK_SECRET` | секретный сегмент URL вебхука |
| `ADMIN_SECRET` | секретный сегмент URL админки |
| `SMTP_USER` / `SMTP_PASSWORD` | почта отправителя (для Яндекс 360 — пароль приложения) |
| `TG_BOT_TOKEN` | бот для отчётов и алертов |

Товары — в `catalog.json`: артикул из Тильды → название и имя файла в папке
на Диске. Сопоставление идёт по артикулу, запасной путь — по названию товара.
Если товар не опознан, письмо покупателю **не уходит**, владельцу падает алерт.

## Админка

`https://<ваш-домен>/admin/<ADMIN_SECRET>` — последние 30 заказов, статусы,
сколько раз скачали, кнопка «перевыпустить и отправить». Открывается с телефона,
так что на жалобу «не могу скачать» можно ответить в одно нажатие.

## Что ещё умеет

- Копия каждого письма кладётся в IMAP-папку «Отправленные».
- Сторож: если через сутки после письма покупатель ни разу не скачал файл,
  владельцу приходит уведомление в Telegram. Молчащий недовольный покупатель —
  худший вид жалобы, лучше написать первым.
- Повторный вебхук по заказу, который не дошёл до письма, обрабатывается
  заново, а не отбрасывается как дубль.
- Ежедневный бэкап базы, 14 копий.

## Грабли, на которых мы уже посидели

**Подключить сервис в настройках сайта Тильды недостаточно.** В самом блоке
формы или корзины (Контент → «Подключенные сервисы») новый сервис появляется
со снятой галочкой. Пока её не поставить, не сохранить блок и не опубликовать
страницу, боевые заказы уходят мимо интеграции — при этом кнопка «тест»
в настройках проходит успешно, потому что Тильда шлёт тестовый запрос напрямую.
Проверять фактом:

```bash
curl -s https://ваш-магазин.ru/ | grep -oE 'name="formservices\[\]" value="[^"]*"'
```

Сервисов должно стать на один больше, чем было.

**В вебхуке включить «передавать данные по товарам массивом», «передавать
externalid» и «отправлять только после оплаты».** Последнее снимает риск
выдать товар до фактической оплаты.

**Юникод в именах файлов.** Файлы, залитые на Диск с macOS, лежат там в NFD
(«й» = «и» + U+0306), а в `catalog.json` имя обычно попадает в NFC — Диск
на такой путь отвечает 404, покупатель видит ошибку. Сервис пробует оба
варианта нормализации, но если сверяете имена руками — сравнивайте через
`unicodedata.normalize`, а не байт в байт.

**Хостинг может резать исходящий SMTP.** У ряда провайдеров порты 25/465/587
закрыты по умолчанию, при этом HTTPS работает и проблема выглядит как что
угодно, кроме блокировки. Открывается тикетом в поддержку: транзакционные
письма покупателям, десяток в месяц, SPF/DKIM настроены.

**Временная ссылка Яндекс.Диска живёт около 4 часов** и переиспользуется,
к IP не привязана. Для стриминга сервис берёт её на каждый запрос заново.
